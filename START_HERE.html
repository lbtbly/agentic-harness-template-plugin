Claude Code plugin marketplace · autonomous coding

One engineer, asleep.
Several features, shipping.

Run a coding agent unattended overnight — packaged as plugins, gated where it counts, and built around the one hard problem: knowing when the work is actually done.

You launch one command before bed. By morning, a queue of features has been built in parallel, verified end-to-end, and the safe ones have merged themselves to a green main — while anything risky or ambiguous waits, clearly, for you.

📦 5 plugins, installed not copied 🧪 321 assertions, built test-first 🧑‍⚖️ human-gated where it counts 💳 subscription-friendly (no API key required)
The load-bearing idea: an agent must never be the judge of its own completion. "Done" is an external, machine-checkable contract — get that wrong and the run either quits early or never stops. Everything here serves that one truth.
Mental model

Three laws to design against

The model is the engine; the harness is everything around it that makes an unattended run safe, verifiable, and resumable.

🧠The repo is the only memory

Each session starts amnesiac — like shift workers who never met. Anything not in the repo, git history, or the state layer does not exist next session. Externalize state; never rely on the conversation.

🔍Verification is the bottleneck

Generation is cheap; trustworthy verification is not. The whole game is moving "is this correct?" off the human and into mechanical loops — tests, browser checks, linters, adversarial reviewers.

🧑‍✈️Humans steer, agents execute

You design the environment, specify intent, and own the gates that carry product and security judgment. The machine does the volume between those gates.

🔧A failure is a harness bug

When the agent fails, the question is never "try harder" — it's "what capability or signal was missing, and how do I make it legible and enforceable?"

What it must defeat

The four ways an overnight run rots

01

One-shotting

Tries to do everything at once, exhausts its context mid-feature, leaves a half-built mess. Parry: one unit of work per session; a locked scope.

02

Premature victory (project)

A late session sees progress and declares the whole project finished. Parry: a feature list that defines finished — done when every item passes, not before.

03

Premature victory (feature)

Marks a feature done after a unit test or a curl, never exercising it as a user would. Parry: end-to-end browser verification, defined up front.

04

Dirty state

Leaves bugs and disordered code the next shift inherits at interest. Parry: "clean state" = mergeable; commit + progress note every session.

Getting started

Install the plugins

It ships as a plugin marketplace, not a copied repo: one versioned dependency many projects share and upgrade in place. Installing a plugin is the on/off switch; skills are namespaced (/orchestrator:run, /orchestrator:kickoff, …).

# add once, install the core, then reload so its skills register
/plugin marketplace add your-org/agentic-harness-template-plugin
/plugin install core@harness
/reload-plugins

# stand up a project, then add the autonomous loop
/core:new-project
/plugin install orchestrator@harness   &&   /reload-plugins
/orchestrator:enable-orchestrator
The reload gotcha

A freshly installed plugin's skills are "Unknown command" until you run /reload-plugins. It's baked into every install instruction here — the single most common "why doesn't the command exist" stumble.

Two prompts, one harness

/core:new-project is the initializer — it builds the environment once (feature-list scaffolds, a one-command app launch, the first commit). Every session afterward is the same coder prompt: incremental progress, one unit, clean exit.

How it runs

Two flavors, and a typical day

gated Scheduled nightly — the recommended default

A scheduled build produces one PR per epic overnight; each morning you review and merge. Every human gate stays — plans approved by you, nothing reaches main without your per-PR OK.

auto Run-to-completion

/orchestrator:run — launch and it runs until your chosen scope is drained: low-risk epics auto-merge, high-risk escalate. Keeps the plan gate, trades the per-PR merge gate for a risk gate. Turn on after the gated flavor has earned your trust.

A day in the gated flavor — one morning touchpoint

~09:00

you Review last night's PRs

The digest arrives — your worklist. Per PR: test it on staging following the ordered sequence, then leave one signal: /orch approve or /orch revise: <notes>. Give the high-risk flags the closer read.

~11:00

you · ~15 min Run /orchestrator:kickoff

Reads your OK/revise signals from the forge (matched via the orch/<id> branch), risk-checks then merges OK'd + green PRs one-by-one (full suite after each; a red merge is reverted), queues commented PRs for rework, drafts plans for new epics — you approve each plan live (the plan gate) — then partitions files and detaches.

~12:30 →

the machine The build runs itself

Fires on the schedule inside the egress-locked sandbox under its own permission profile: one worker per epic in its own worktree — reworks the commented ones, builds the new ones, integrates serially, checks overlaps, deploys staging, writes tomorrow's digest. A usage limit pauses it; it resumes on reset.

The loop

Run-to-completion, as a pipeline

The driver owns an outer loop. Steps 1–2 need you briefly at launch; 3–7 run unattended until your selected scope is drained or a guard trips.

01

Launch & scope

All epics in order, or the first N — it lists their names to confirm, and folds in the previous run's PR feedback.

02

Plan

Oversized initiatives decompose into right-sized epics; any epic without a DoD gets one authored. An independent reviewer validates each DoD against intent before a line is built.

03

Build — concurrently

One subagent per epic, each in its own git worktree, up to a cap. Epics partition into waves by file footprint: disjoint run together, heavy overlaps defer.

04

Verify — the DoD

Each epic loops build → verify → improve until the independent four-stage DoD passes. A no-progress guard breaks stubborn epics out to escalation.

05

Integrate & merge — serially

A single merge queue: integrate → cross-epic regression → risk classify → low → auto-merge to a green main (suite re-runs; auto-revert on red) or high → escalate.

06

Guard & throttle

Budget, wall-clock, no-progress, thrash and safety guards bound the run; a usage monitor slows and pauses before hitting limits, then resumes on reset.

07

Terminate

Ends when every selected epic is merged or escalated — or a hard guard trips with a clean checkpoint. It never declares the product done; only "the scope you picked is resolved."

The crux

The definition of done

If "done" is only "the tests pass," the agent ships things that pass but are wrong. A trustworthy DoD spans engineering, product, and design — and is checked by something other than the thing that built it.

// per-epic .orch/epics/<id>/feature_list.json — the termination authority
{
  "epic": "checkout-v2",
  "acceptanceCriteria": [{ "id":"ac1", "statement":"user can pay with a saved card", "automated":true }],
  "testLevels": { "unit":true, "integration":true, "e2e":true },
  "epicTests": ["tests/checkout/pay.e2e.ts"],
  "designRefs": ["docs/design/checkout.png"],
  "features": [{
    "id":"f1", "description":"pay with saved card",
    "steps":["open /checkout","choose saved card","confirm"],
    "expected":"order confirmed, receipt shown", "passes": false
  }]
}

JSON, not Markdown — models corrupt structured files far less. The only permitted mutation is flipping passes to true after a real pass; editing or deleting steps to look complete is prohibited by contract and enforced by validate-dod.

1️⃣Tests, every level

Unit + integration + e2e, plus the tests authored for this epic; typecheck + lint clean. Never weaken a test to pass — fix the code.

2️⃣Functional E2E, as a user

Drive the running app in a real browser (Playwright / browser MCP), walking each feature's steps. Invisible surfaces go to blindspots, never silently passed.

3️⃣Acceptance assertions

Each product-level criterion checked — automated where possible, judge-evaluated otherwise.

4️⃣Independent judge panel

Adversarial reviewers with distinct lenses (correctness / pm / design) — and distinct models per lens, because same-model votes correlate. Pass = strict majority AND no blocking objection; dissent escalates.

// what verifyDoD(epic) returns — the merge queue's input
{ "epic":"checkout-v2", "done": false, "escalate": true,
  "stages": { "tests":"pass", "e2e":"pass", "acceptance":"pass", "judge":"fail" },
  "blocking": ["judge:correctness"], "reasons": ["saved-card path 500s on expired token"] }
No self-grading

The chain is separate at every link: the planner authors the DoD → an independent design-reviewer validates it against intent → the builder implements → an independent judge panel verifies → the forge (checks + CODEOWNERS) gates the merge. Human intent — the initiative you launched — is the root ground truth.

Honest limit

The judge panel is the load-bearing weak link — an LLM judging an LLM. Mitigations: diverse lenses and models, majority + blocking-dissent, auto-merge only for low-risk, and a morning report a human skims. Vision misses things (native modals, subtle regressions) — design-heavy work is flagged for human eyes. This is why auto-merge is scoped, not universal.

Throughput

Parallel build, serial merge

Build wide, land narrow. Many epics build at once in isolated worktrees; a single serial queue lands them so concurrency can never race main into a broken state.

🌳Isolation

One git worktree per epic (orch/<id>); parallel builders physically cannot touch each other's files.

🌊Waves

The planner's footprint per epic partitions work: disjoint footprints run together; heavy overlaps go to a later wave to cut rework.

🚧The merge barrier

Done epics queue: integrate → cross-epic regression on overlaps → risk-gate → merge or escalate → re-run the suite on main, auto-revert on red → recreate the integration branch.

🔁Resumability

Git + the forge are the source of truth. A killed or paused run re-reads reality and continues; orphaned epics re-queue. Pause/resume and crashes are safe.

Bounds

Guards & usage throttling

The agent is never the authority on when to stop globally — external guards are. Defer (pause and resume) ≠ halt (checkpoint and end) ≠ skip (drop one epic, keep going).

GuardScopeEffect
No-progressper epicK improve rounds with no movement → mark blocked, escalate, move on
Usage throttlerunnear the ceiling → drop concurrency → pause → auto-resume on reset (defers)
Budgetrunhard token/cost cap → checkpoint + halt
Wall-clockrun"until 07:00" / max duration → checkpoint + halt
Thrashruna whole cycle advances zero epics → halt + escalate
Safetyrunsettings tampered / branch protection gone / sandbox down → abort
Throttle, don't crash

Rate limits (429s) ride the CLI's own backoff. Hard limits (a weekly/daily cap) never sleep in-process for hours — pending epics checkpoint as Paused with paused-until <ts> and their origin state, the run exits cleanly, and a retry lane resumes after the reset. The loop also picks its own weight class per epic — a cheaper model for mechanical work, a stronger one for large/risky footprints, escalating once on a hard failure.

What you wake up to

The morning report

Not a log to grep — a single, immutable digest written for a human with coffee. One self-contained HTML file per day (docs/reports/nightly/<date>.html); a same-day re-run appends a "Run 2" section, never overwrites. Delivered to Slack/email at a time you choose, and persisted to an orch/state branch so a build that finished past midnight still reaches you.

✅Per epic

Summary + PR link + risk class (low = auto-merged; high = escalated with the reason), the four DoD gate results, and the staging route where it's live to click through.

🧭Your ten-minute check

The top of the digest is an ordered, human-runnable test sequence: per-epic acceptance checks (action → expected + staging URL), then cross-epic interaction tests wherever footprints overlapped. Pause/resume markers are visible, never silent.

The floor that never moves

Safety model

Two tiers: core guarantees can't be switched off by any profile or mode; the rest apply when the orchestrator runs. Autonomy never trades away a control — it moves the human gate (to scope-at-launch, plan approval, and high-risk), it doesn't remove it.

🔑Secrets stay secret core

Three independent walls (gitignore + deny rules + secret-guard hook), working with variable names, never values. In unattended CI the fail-closed egress firewall is the control — nothing can phone out.

🚫No self-elevation core

It cannot edit the file defining its own permissions, nor the guardrail hooks or allow-listed scripts it runs. It must not rewrite its own referee. One documented Bash-redirection gap stays open deliberately — the real fences are plan-mode, the sandbox, and PR review.

✋Reads before it writes core

Plan-mode by default — it proposes before it writes — and every MCP server is approved one by one.

🧹Git hygiene

Can't skip git safety checks (--no-verify), can't force-push main, can't quietly edit CI files, lockfiles, or accepted ADRs (supersede instead).

🔒Main is gated orchestrator

Gated: nothing reaches main without your per-PR OK + green checks. Run-to-completion: low-risk auto-merges after DoD + judges + the CODEOWNERS double gate; high-risk escalates. Workers only push throwaway orch/* branches.

🧪Risky changes: a second gate orchestrator

Big diffs or anything touching auth / payments / migrations / infra are auto-flagged, need a security-auditor pass to be merge-eligible, and CODEOWNERS forces a human review at the forge — risk gated twice, independently.

📦Unattended runs are boxed in orchestrator

Egress-locked devcontainer + the native OS sandbox, under the loop's own permission profile; your everyday committed settings are never touched.

🛑Escalation is the default

Unknown risk classifies high (fail closed); a crashed consistency checker keeps the deploy gate shut; a red post-merge suite auto-reverts.

// orchestrator/risk-policy.json — data the operator owns; re-read every run
{ "linesChanged": { "low": 150, "medium": 600 },        // > medium ⇒ high
  "highRiskPaths": ["**/auth/**","**/payment/**","**/migrations/**","**/infra/**",".github/workflows/**"],
  "autoMergeRiskLevels": ["low"],                        // only these merge unattended
  "requiredReviewByRisk": { "low":"judge-panel", "high":"human-codeowners" } }

Rules of thumb

Parallel only if files are disjoint — read-only agents parallelize safely; writers get worktrees. Vague invocation is failure mode #1 — exact paths + a success criterion, always. Below ~3 independent subtasks, coordination costs more than it gains.

Memory

The state layer

Sessions, specs, epics, plans and status all go through one CLI contract with a pluggable backend — plain sharded files in the repo (none, zero-setup) or your real board (GitHub Projects / GitLab / Jira / Linear / Notion / Trello adapters).

# the contract — same ops on every backend
orch state health                         # backend reachable / auth OK
orch state push-session < session.json    # end-of-session snapshot
orch state pull-session                   # startup injection reads here
orch state push-epic · push-status        # one file per epic — no shared table
orch state pull-status                    # aggregated AT READ TIME
orch state pull-feedback                  # ALWAYS from the forge (gh/glab)
orch state push-digest --date D < d.html  # the daily report

🧩Sharded, not shared

One small file per branch/epic — two parallel workers never write the same file, and git merges them with zero conflicts (property-tested). Status aggregates at read time.

✉️State ≠ feedback

Tasks can live anywhere, but approvals are always read from the code host, never the board. Signals only count from trusted authors (owner/member/collaborator).

🏛️The board outlives the loop

Chosen once at scaffold, reused when you enable autonomy, left fully intact when you disable it.

🛟Fail-open injection

At session start it reads local → remote (with a timeout) → cache — a slow board never stalls a session; a corrupt state file is skipped loudly, never blanks the board.

Provenance

Tests & verified deviations

Every subsystem shipped test-first, in this order — each green before the next: ① the DoD contract + independent verifier, ② the planner, ③ the driver + concurrency + guards, ④ risk-gated auto-merge + safety wiring, ⑤ packaging + docs. Before building, each design was checked against the July 2026 state of the art; the deltas live in docs/DEVIATIONS.md.

⚖️Judge panel, decorrelated

Same-model majority votes ≈ one judge (correlated-errors research), so each lens pins a distinct model; ties and zero votes always fail.

🔐Risk fails closed

Risk is computed from the real git diff; a missing policy, unknown branch, or unreadable diff classifies high — nothing merges on a shrug. (Fixes a reference-implementation gap where the loop hardcoded low.)

🎫Auth lanes, verified

Subscription lane first: claude setup-token → CLAUDE_CODE_OAUTH_TOKEN (~1 year), never combined with --bare (which skips OAuth). ANTHROPIC_API_KEY is the metered lane and takes precedence — leave it unset otherwise.

🏖️Native sandbox on top

Claude Code's OS sandbox (write-scoping, credential deny, network allowlist) is enabled in the unattended profile, in addition to the devcontainer's egress firewall.

If you build one thing first

Build the definition-of-done contract and its independent verifier before the fancy driver. The loop is easy; a trustworthy "done" is the hard, valuable part. Once an epic can be proven finished by something other than its author, everything else — concurrency, auto-merge, scheduling — is plumbing you add incrementally, gate by gate.

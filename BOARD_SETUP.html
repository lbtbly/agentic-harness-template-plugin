Setup guide · one page per backend

Provision the board.
Then the loop has somewhere to think.

The board is the golden source: every initiative, epic and task lives there, and .orch/ is only a working mirror. This page gets one ready, click by click, for Linear, Notion or Jira.

Twenty minutes, once. /core:board-setup automates most of it — this is what it does, and what it cannot do for you because no API exposes it.

UI paths verified against vendor documentation on 27 July 2026. Vendors move menus; if a path is stale, the Settings search box in each tool finds the page by name.
The contract

What the framework actually needs

Only three things, whatever the tool. Everything else on this page is one vendor’s way of expressing them.

📏A place per work item

One card per epic, carrying an id in its title as [epic-id] Title. The full record travels as JSON inside the card — the human-readable fields are the view, not the source.

🏁Twelve lifecycle states

The loop moves cards through them. Your board does not need twelve columns — the map is many-to-one, so five real states are enough.

🔑A token, eventually

Only when the unattended loop runs. Provisioning interactively needs none. Names never values (docs/SECURITY.md).

The twelve states

Suggested

Machine-proposed. The night loop never builds from this lane.

Backlog

Filed, not yet planned.

Needs-plan

Awaiting a plan.

Planned

Plan approved — cleared to build.

In-progress

A worker is on it.

Needs-review

PR open, awaiting your signal.

Changes-requested

Back for rework.

Approved → Merged

Landed.

Blocked

Failed N attempts — human triage.

Paused

Usage-limit checkpoint. Auto-resumes.

Cancelled

Rejected suggestion.

The split everything rests on

The board shows state. Your approvals are read from the forge — the pull request — never from the board. Commenting /orch approve on a Notion page or a Jira issue does nothing. That is deliberate: the thing that gates a merge should be the thing that shows the diff.

The backend is a line in state.config.json and the board outlives enabling or disabling the loop. Run on none for a week, then provision a real board when you want other people to see the work.

Backend 1 of 3 · least setup

Linear

Nothing needs creating. A Linear team already has workflow states and labels, so this is naming what exists and writing four lines of config.

  1. Find your team key

    It is the prefix on every issue id — the ENG in ENG‑123. Everything the harness does is scoped to one team.

    Settings›Teams lists them if you are unsure.

  2. Look at the team’s issue statuses

    Settings›Teams›your team›Issue statuses

    A new team ships with exactly five, in this order: Backlog · Todo · In Progress · Done · Canceled. Statuses belong to categories — Backlog, Unstarted, Started, Completed, Canceled — and the category is what Linear uses for its own logic, so put any new status in the right one.

    There is no “In Review” by default. A lot of guidance assumes there is. If you map Needs‑review to a status that does not exist, health tells you and that state silently falls back to a label instead.

  3. Optional, 30 seconds, worth it: add In Review

    On the same screen, add a status named In Review in the Started category, positioned after In Progress. It separates “being built” from “waiting on you” — which is exactly the distinction you act on each morning.

  4. Write the config

    In your repo, orchestrator/state.config.json. This is the stock-team map — every target exists on a brand-new team, so it works with no Linear changes at all:

    {
  "backend": "linear",
  "forge": "github",
  "linear": {
    "teamKey": "ENG",
    "stateMap": {
      "Suggested": "Backlog",     "Backlog": "Backlog",
      "Needs-plan": "Backlog",    "Planned": "Todo",
      "In-progress": "In Progress",
      "Needs-review": "In Progress",
      "Changes-requested": "In Progress",
      "Approved": "Done",         "Merged": "Done",
      "Blocked": "Todo",          "Paused": "Todo",
      "Cancelled": "Canceled"
    }
  }
}

    If you added In Review in step 3, point Needs-review and Changes-requested at it instead.

  5. Create a Project per initiative — only if you want the native tier

    Sidebar Projects›+ Create project. An epic whose initiative field matches a project name is filed under it, and list‑initiatives then reads the real tier instead of deriving one.

    The adapter never creates projects

    Conjuring a project from a free-text field is how boards get littered. No match → a warning on stderr, the value stays in the record, the run continues.

  6. Labels: nothing to do

    orch-epic, orch-child, orch-state-* and orch-complexity-* are created on demand. On a governed workspace set "createMissingLabels": false — the lifecycle then relies entirely on stateMap.

How the harness maps onto Linear

HarnessLinearMechanism
initiativeProjectprojectId on the issue
epicIssuelabel orch-epic, title [id] …
child / taskSub-issueparentId, label orch-child
lifecycle stateIssue statusstateMap, label fallback

Epics are Issues rather than Projects because the contract is issue-shaped — twelve states, labels, an assignee carrying the claim, a PR number, and a description that can hold the record. Linear Projects have a five-value status enum and none of that. Full reasoning in ADR-0029.

Backend 2 of 3

Notion

Two databases and three commands. Notion is the only backend where the initiative is a real page with its own board and state, rather than a derived grouping — which is why it takes one more step than the others.

Let the connector do it

If your session has a Notion connector, /core:board-setup runs all of this as SQL DDL. The steps below are what it does — worth reading once, because two of them are things no API can fix afterwards.

How the harness maps onto Notion

HarnessNotionMechanism
initiativePage in a second databaseInitiative relation
epicPage, Type = Epictitle [id] …
task / childPage, Type = TaskParent epic self-relation
lifecycle stateState selectthe 12 options are the columns

The Type property is not decoration. Without it, epics and tasks sit in one flat table with nothing telling them apart — for you or for the agent. Jira and Linear have always distinguished them with labels; this is Notion’s equivalent.

  1. Create the Initiatives database first

    The epics database relates to it, so it has to exist first.

    CREATE TABLE ("Name" TITLE,
              "State" SELECT('Backlog':gray, 'In-progress':blue, 'Merged':green),
              "Initiative ID" RICH_TEXT)

    Keep the id it returns — that is <init_ds> below. By hand: /database → Database — Full page, then add the two properties.

  2. Create the Epics database, related to it

    CREATE TABLE ("Name" TITLE,
              "Type" SELECT('Epic':purple, 'Task':gray),
              "State" SELECT('Suggested':gray,'Backlog':gray,'Needs-plan':brown,
                             'Planned':orange,'In-progress':blue,'Needs-review':yellow,
                             'Changes-requested':red,'Approved':green,'Merged':green,
                             'Blocked':red,'Paused':gray,'Cancelled':default),
              "Epic ID" RICH_TEXT,
              "Initiative" RELATION('<init_ds>', DUAL 'Epics' 'epics'),
              "Assigned to" RICH_TEXT,
              "Complexity" SELECT('low':green, 'medium':yellow, 'high':red),
              "PR" NUMBER, "Note" RICH_TEXT, "Updated" DATE)
    Name both sides of the relation. A bare DUAL gives the other database an auto-generated inverse called Related to <database> (Initiative) — and you cannot rename it from the DDL afterwards. DUAL 'Epics' 'epics' names it properly. (I found this the hard way; no documentation mentions it.)

  3. Add the self-relation for tasks — a second call

    It needs the epics database’s own id, which only exists after step 2.

    ADD COLUMN "Parent epic" RELATION('<epics_ds>', DUAL 'Sub-tasks' 'subtasks')

    One statement creates both sides. Set Parent epic on a task and Notion fills Sub-tasks on the epic itself — nothing writes the inverse, and the harness never tries to.

  4. Set the State options in lifecycle order, then group by State

    Switch to a Board view, then …›Group›State. Columns inherit the option order.

    Worth adding a second view filtered to Type = Epic — a clean epic board with the tasks tucked away.

    Some clients append options alphabetically. If Approved sits above Backlog, drag them into lifecycle order now. The public API cannot configure a view, so this is human-only — and it is inherited by every board built on the property.

  5. Record both ids

    {
  "backend": "notion",
  "forge": "github",
  "notion": {
    "dataSourceId": "<epics_ds>",
    "initiativesDataSourceId": "<init_ds>"
  }
}

    Already running an older board? A config with just "databaseId" still works — the adapter resolves the data source once and tells you to record the id.

  6. Create the integration and share both databases

    Go to app.notion.com/developers/connections (workspace owner required), create a connection, copy its installation access token from the Configuration tab.

    Then for each database: open it → ••• top right › Add connections › your integration.

    Both. Not just the epics one. A related database that is not shared makes every relation read 404 — and the error looks like a wrong id, not a permissions problem. orch state health probes the Initiatives database on purpose and names this cause, because the raw error does not.

    Export the token as NOTION_TOKEN. The name goes in .env.example; the value never touches the repo.

Every piece is optional

Skip the Initiatives database, or the self-relation, or Type, and the board still works — that part of the hierarchy simply lives in the record JSON instead, exactly as it did before. health tells you what is missing and capabilities reports hierarchy: derived rather than native. Nothing breaks; you just see less.

Backend 3 of 3 · most manual

Jira

Jira is the only backend with a step no API can do for you: statuses and columns are created by hand. Neither the REST API nor any connector can create a status or reconfigure a workflow. Everything else is automatable.

Answer this first

Is this a fresh project dedicated to the harness, or an existing project with your team’s real work in it? Fresh → give it one column per lifecycle state and use an identity map. Lived-in → change nothing. Statuses, workflows and issue types belong to that team; map many-to-one onto what already exists and skip the column step entirely.

  1. Create or pick a project

    A team-managed Kanban project is the easiest to configure, because its board owns its own statuses. Note the project key — the ENG in ENG‑123.

    No connector can create a Jira project, so this is manual whichever route you take.

  2. Fresh project only: add the columns

    On the board, a column is a status. Add one per lifecycle state:

    + at the right of the columns adds one (creating the status with it) · select a column name to rename it, or •••›Rename · drag a column by its top to reorder.

    For advanced configuration: sidebar Space settings (formerly Project settings) ›Board, which opens Columns and statuses.

    Two prerequisites. Work items must be grouped by status (the default), and the space must use a single workflow — otherwise Jira disables column editing on the board and you must go through workflow admin instead.

  3. Map the twelve states onto real statuses

    Many-to-one is fine and expected. For a stock board (Idea / To Do / In Progress / Testing / Done):

    {
  "backend": "jira",
  "forge": "github",
  "jira": {
    "projectKey": "ENG",
    "epicIssueType": "Epic",
    "childIssueType": "Task",
    "statusMap": {
      "Suggested": "Idea",
      "Backlog": "To Do",       "Needs-plan": "To Do",
      "Planned": "To Do",       "Blocked": "To Do",
      "Paused": "To Do",
      "In-progress": "In Progress",
      "Needs-review": "Testing", "Changes-requested": "Testing",
      "Approved": "Done",        "Merged": "Done",
      "Cancelled": "Done"
    }
  }
}

  4. Create the API token — unattended loop only

    Go to id.atlassian.com/manage-profile/security/api-tokens › Create API token. Name it, set an expiry (1–365 days), and copy it immediately — it is shown once.

    Create an unscoped token, not a scoped one. Atlassian now offers Create API token with scopes, and those tokens must be called against https://api.atlassian.com/ex/jira/<cloudId> — not your <site>.atlassian.net URL. The adapter uses the site URL with Basic auth, which is the unscoped pattern. Pick a scoped token and every call 404s against a base URL that looks correct.

    Export JIRA_BASE_URL (https://<site>.atlassian.net), JIRA_EMAIL, JIRA_API_TOKEN. Names in .env.example; values never.

How the harness maps onto Jira

HarnessJiraMechanism
epicEpic issue typelabel orch-epic, summary [id] …
child / taskTask under the Epicparent link, label orch-child
lifecycle stateStatusworkflow transition, label fallback
initiative—derived from the record
A workflow is a graph, and that matters

Unlike Linear, Jira reaches a status by transition — and the one you want may not be reachable from where the issue currently sits. The adapter attempts one direct hop and, failing that, falls back to the orch-state-* label for that update and logs it. A mis-mapped board degrades; it never breaks the run.

the adapter: pm-jira.js · ADR-0021 · test-pm-jira.sh — browse the source in the overview.

Prove it

Verify it works

Three commands. Run them in order — each one fails in a different, informative way.

# 1. can we reach the board, and is the state map real?
orch state health

# 2. round-trip one card
echo '{"id":"board-smoke","title":"smoke","state":"Backlog"}' | orch state push-epic
orch state pull-status          # the card appears here…
                                # …and on the board. Then delete it.

# 3. does the hierarchy read back?
orch state list-initiatives

✅What good looks like

health returns {"ok":true,"backend":"<yours>"} and, if you configured a map, missing: []. Every name in your map exists on the real board.

⚠What a warning means

health names each mapped status the board does not have. Those states fall back to labels — the loop still works, the board just reads coarser. Fix it or accept it deliberately.

No token yet? That is expected

Until the unattended loop is enabled, health failing with “LINEAR_API_KEY not set” is the correct answer, not an error. Provisioning interactively needs no credentials at all.

One more thing

Before the unattended loop runs

A remote backend pushes state from inside the sandbox. If its host is not reachable there, every orch state push-* fails closed mid-run — which reads as the loop mysteriously losing its state rather than as a network error.

Uncomment your backend’s host in orchestrator/egress-allowlist.txt and mirror it into both enforcers — the native sandbox (settings.orchestrator.json) and the devcontainer firewall (init-firewall.sh). A parity test checks they agree.

BackendHost to allow
linearapi.linear.app
notionapi.notion.com
jira<your-site>.atlassian.net — per tenant, no fixed host
gitlabgitlab.com, or your self-hosted host

They ship commented out on purpose: every entry widens the blast radius of an unattended run. /orchestrator:enable-orchestrator refuses to enable the loop until the configured backend’s host is allowed.

Things that are true of every backend

🔑Names, never values

A token value never enters the repo, a config file, or a chat message. .env.example carries the name; the value lives in your vault or CI secrets.

🔄Adopting is additive

Pointing the harness at an existing board never deletes, renames or re-types anything. Gaps are reported; fixes only add.

📦Disabling keeps the board

/orchestrator:disable-orchestrator leaves the board and every card intact. The board outlives the loop.
